# Fork 项目治理 — 操作手册

> 本手册解决一个核心问题：
> **如何在持续吸收上游更新的同时，稳定维护本地魔改，且让任何无上下文的 AI / 工程师都能接手。**

---

## 项目变量配置（首次使用时填写）

> 将以下占位符替换为实际项目值，全文保持一致。后续所有章节直接引用已填写值。

| 占位符 | 含义 | 填写示例 |
|--------|------|---------|
| `{{FORK_PROJECT}}` | Fork 项目名称 | `DrcomoDevClaw` |
| `{{UPSTREAM_PROJECT}}` | 上游项目名称 | `OpenClaw` |
| `{{FORK_ROOT}}` | Fork 仓库根路径 | `/path/to/fork/` |
| `{{AUDIT_LOG}}` | 魔改审计日志路径（相对仓库根） | `docs/LOCAL_CHANGELOG.md` |
| `{{RELEASE_LOG}}` | 项目发布日志路径（相对仓库根） | `CHANGELOG.md` |
| `{{REQUIREMENTS_DOC}}` | 当前业务需求文档路径（阶段性，完成后归档） | `docs/requirements/current.md` |
| `{{USER_DOCS_DIR}}` | 用户使用手册根目录 | `docs/` |
| `{{INTEGRATION_CTX}}` | 跨仓联调上下文文档路径 | `references/integration-context.md` |

## 触发条件（直接执行）

当以下场景出现时，走本手册对应流程：
- 要在 `{{FORK_PROJECT}}` 上写代码 → §1 开工检查 → §2 魔改分类 → §5 提交 → §6 回写 → §7 文档同步
- 要同步上游更新 → §3 上游同步 SOP
- 要跨仓联调 → 读取 `{{INTEGRATION_CTX}}`
- 要查历史决策 → 读 `{{AUDIT_LOG}}`
- 要查当前业务需求 → 读 `{{REQUIREMENTS_DOC}}`（阶段性文件，需求完成后归档）

## §1 开工检查

写代码前逐项确认，缺任何一项不准动手：

- [ ] 需求来源：业务需求文件中的 ID，或上游同步批次号
- [ ] 改动范围：改哪些模块、不改哪些模块
- [ ] 魔改类型：Protected / Override / Extension / Patch（见 §2）
- [ ] 验收标准：怎样算"做完了"
- [ ] 回滚方案：出问题怎么退

---

## §2 魔改分类

每次本地改动必须归入以下之一：

| 类型 | 含义 | 上游同步时的处理 |
|------|------|-----------------|
| **Protected** | 核心魔改，上游不会有对应实现 | 冲突时优先保留我们的意图，语义合并上游改进 |
| **Override** | 上游有实现但我们需要不同行为 | 三路思考：上游改了什么？我们为什么覆盖？能否同时满足？ |
| **Extension** | 上游没有的纯新增功能 | 通常无冲突，但需确认上游新版本是否提供了类似能力 |
| **Patch** | 对上游 bug 的临时修复 | 上游修复后删除本地 patch |

### 最小侵入原则

- 能用 Extension 就不用 Override
- 能用 Override 就不用 Protected
- 改动越靠近上游原始结构，同步成本越低
- 禁止顺手跨域重构——每批次只解决一个问题域

## §3 上游同步 SOP

### Step 1：影响分析（不改代码）

```bash
git fetch upstream --prune
git log --oneline main..upstream/main | wc -l
git diff --name-only main upstream/main
```

将上游变更文件对照 §2 魔改分类，分为三类：
- **Safe**：上游改了但我们没改过，或属于 Patch 类（上游已修复）→ 直接采用
- **Conflict-prone**：Protected / Override 区域且上游也改了 → 需要人工或 AI 介入
- **New**：上游新增文件 → 直接采用

同时对照当前业务需求文件，识别高风险行为域。

### Step 2：按批次实施

- 先处理安全修复和阻断项
- 每批次限制改动范围，独立验收
- merge 无冲突 ≠ 行为无回归——必须跑验收三层

### Step 3：验收后合并

契约 + 回归 + 冒烟全部通过后，方可合入。

### Step 4：回写

更新 `{{AUDIT_LOG}}`（格式见 §6）。如有 Patch 类改动被上游修复，标记为 `[已被上游修复，可删除]`。

---

## §4 执行约束与验收

### 执行约束

- 涉及安全边界（文件外发、会话路由、权限校验）时，默认 fail-closed
- P0 先做，P1/P2 排后
- 保持最小改动

### 验收三层

| 层级 | 验什么 |
|------|--------|
| 契约验收 | 行为语义是否满足需求 |
| 回归验收 | 关键历史能力是否被保留 |
| 冒烟验收 | 主链路是否真实可跑 |

P0 项三层全过才放行。

## §5 提交规范

### 提交信息格式

```
<scope>: <简述>

魔改类型: Protected / Override / Extension / Patch
需求来源: <业务需求ID 或 上游同步批次号>
验收: [契约✓ 回归✓ 冒烟✓]
风险: <如有>
```

示例：
```
<scope>: 修复 <模块> 在 <场景> 下的 <问题>

魔改类型: Protected
需求来源: <需求ID>
验收: [契约✓ 回归✓ 冒烟✓]
风险: <如有，否则删除此行>
```

## §6 审计日志（`{{AUDIT_LOG}}`）回写规范

`{{AUDIT_LOG}}` 是 fork 魔改的决策审计日志，与仓库根目录 `{{RELEASE_LOG}}`（项目发布日志）完全独立。

**何时写**：每次涉及本地魔改的代码提交后。

**条目格式**：

```markdown
## YYYY-MM-DD <scope>: <简述>

- **魔改类型**: Protected / Override / Extension / Patch
- **需求来源**: <业务需求ID 或 上游同步批次号>（无则写"无"）
- **改动范围**: 涉及的文件/模块
- **决策与理由**: 为什么这样做（why，不是 what）
- **验收结果**: 契约✓/✗ 回归✓/✗ 冒烟✓/✗
- **证据**: 日志路径 / 测试输出 / 截图位置
- **回滚**: 回滚方式
```

**规则**：
- 新条目追加在文件最前面（最新在上）
- 上游同步批次单独记录，列出 Safe / Conflict-prone / New 的处理结果
- Patch 类改动被上游修复后，在对应条目追加标注 `[已被上游修复，可删除]`

## §7 文档维护
### 用户使用手册同步（强制）

当功能变更涉及用户可感知的行为时（新命令、新配置项、行为变化），必须同步更新 `{{USER_DOCS_DIR}}` 下对应的用户使用手册文档。

检查路径（根据实际项目文档结构调整）：
- 新增/修改了命令 → 检查 `{{USER_DOCS_DIR}}cli/`、`{{USER_DOCS_DIR}}automation/` 是否需要更新
- 新增/修改了配置项 → 检查 `{{USER_DOCS_DIR}}concepts/`、`{{USER_DOCS_DIR}}reference/` 是否需要更新
- 新增/修改了平台/渠道行为 → 检查 `{{USER_DOCS_DIR}}platforms/`、`{{USER_DOCS_DIR}}channels/` 是否需要更新
- 新增/修改了 hooks/中间件 → 检查 `{{USER_DOCS_DIR}}gateway/`、`{{USER_DOCS_DIR}}automation/` 是否需要更新

**规则**：功能代码和文档更新应在同一批次完成。禁止功能已合入但文档未更新。

### 更新优先级

当文档与现实不一致时：

1. `{{USER_DOCS_DIR}}` 用户使用手册（用户直接可见，最高优先）
2. `{{INTEGRATION_CTX}}`（路径/接口变化）
3. 当前阶段的业务需求文件 `{{REQUIREMENTS_DOC}}`（需求语义变化）
4. 本文件其他章节（流程变化）

### 质量标准
- 写可执行内容，不写对话式语言
- 写事实和路径，不写感想和建议
- 写给下一个没有上下文的人看

---

## 禁止事项

- 禁止在审计日志 `{{AUDIT_LOG}}` 和项目发布日志 `{{RELEASE_LOG}}` 之间混写条目
- 禁止跳过开工检查直接写代码
- 禁止不标注魔改类型就提交
- 禁止 P0 项未过验收三层就合入
- 禁止顺手跨域重构
- 禁止功能已合入但 `{{USER_DOCS_DIR}}` 用户使用手册未同步更新
